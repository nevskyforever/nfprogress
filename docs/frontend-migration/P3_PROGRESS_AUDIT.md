# P3 progress mutation audit

P3 introduces a typed progress mutation boundary and ports only verified pure
calculations. Projects, stages, and progress remain PKL-authoritative.

## Legacy representation

The authoritative history is `engine.Note` objects in `Project.notes` or
`Stage.notes`, inside `data.pkl`. A note contains:

| Field | Current representation | Boundary behavior |
| --- | --- | --- |
| Stable ID | `entry_id`, generated by `Project._ensure_progress_entry_ids()` for old rows | Preserved as API/SQLite `id`; delete uses it |
| Project/stage | Containing object; stage ID is `Stage.stage_id` | Explicit `project_id` plus optional `stage_id` |
| Created/effective date | `date_create: datetime`; its date is the effective writing day | Serialized as `created_at`; no browser date is inferred |
| Raw total | `Note.new_total` is stored in symbols; input is normalized in the containing entity unit | Returned as converted `new_total` plus `new_total_symbols` |
| Raw delta | `added_symbols` in symbols | Returned as `added_symbols` |
| Converted total/delta | Derived by `engine.unit_converter` | Returned as `new_total`/`added` in entity unit |
| Progress contribution | `added_progress` | Preserved |
| Source metadata | Not on `Note`; source is inferred from entity `work_method` and `synch` | Never client-authored in the typed manual command |
| Edit/revision metadata | Not present | No update operation exists |

The legacy list order is the canonical history order. There is no separate
progress-entry revision or bulk mutation protocol. Existing IDs are therefore
safe to expose, but a future SQLite cutover must retain the list-order and
stable-ID migration rules.

## Mutation surface

| Operation | Frontend caller | API/service | Persisted fields | Unit/date | Stateful effects | P3 boundary |
| --- | --- | --- | --- | --- | --- | --- |
| Manual project add | `ProgressWorkspace` → projects store | `POST /api/projects/{id}/progress` → `ProjectService.record_progress` | project `total_units`, one `Note`, `edit_date` | server rounds; effective writing day | streak, game/rewards, lifecycle rules | typed `add_project_progress` on Tauri; API adapter on Web |
| Manual stage add | `ProgressWorkspace` stage selection | same endpoint with `stage_id` → `record_progress` | stage `total_units`, one `Note`, parent edit date | same | same, with stage/project aggregation | typed `add_stage_progress` on Tauri; API adapter on Web |
| Delete project/stage entry | `ProgressWorkspace` | `DELETE /api/projects/{id}/progress/{entry_id}` → `delete_progress` | removes `Note`, recomputes total from last note | no new date | plan recalculation; no game reversal | typed `delete_progress` on Tauri; API adapter on Web |
| External sync add | Integrations page run/run-all; background worker | sync endpoints → `record_synchronized_progress` | same note plus sync timestamps/config | trusted source mtime validated server-side | sync stale checks, streak/game effects | remains integration/Python-owned; no privileged TS source input |
| In-app document add | document editor | `/api/documents/{id}/progress` → `record_document_progress` | document record then project note | server clock/writing day | app/document/game effects | remains document/Python-owned |
| Word upload add | Word import card | `/api/projects/{id}/imports/word` → integration service and project service | project note when changed | server count and unit conversion | import and project effects | remains integration/Python-owned |
| Edit history entry | no caller/route | unsupported | none | n/a | n/a | explicit future blocker, not fabricated in P3 |
| Reset/rollback/bulk | no progress-specific route found | none | none | n/a | n/a | no operation in current model |

Project/stage create, lifecycle, completion, archive, stage conversion, and
metadata updates can also change project totals or statuses, but they are not
progress-entry mutations and remain outside this boundary. Project reads can
refresh streak status as a legacy side effect; this remains a Python read path.

## Pure vs Python-owned semantics

Moved/reused in TypeScript Core:

- unit factors and symbols/A4/author-list/Ficbook-page conversion;
- author-list ties-to-even conversion and page-like ceiling conversion;
- submitted-total normalization matching `_round_for_unit`;
- progress delta in symbols and percentage contribution;
- total percentage, remaining amount, daily plan/deadline helpers;
- explicit-input writing-day date helper and pure statistics projection.

Python remains authoritative for validation against the real entity, PKL
mutation, list ordering, stale sync source checks, writing-day timestamp
storage, streak/freeze state, game/reward/quest effects, completion/lifecycle,
document/integration state, and mirror recovery. TypeScript calculations are
previews and parity-tested helpers, not a security or business authority.

The current writing-day contract stores the effective writing date in
`Note.date_create`. The frontend consumes that serialized date and does not
recalculate it from `Date.now()`. Pure helpers accept an explicit local `Date`
and start time; DST-sensitive persistence and imported timestamps stay in
Python.

## Safety findings

- Manual Tauri commands accept only project/stage IDs and a finite,
  non-negative `newTotal`; `source`, `work_method`, timestamps, and arbitrary
  payload fields are not accepted.
- Python treats an existing legacy `synch` binding as authoritative even when
  an old record lacks the newer `work_method` field. Manual writes therefore
  cannot bypass synchronized-entity validation.
- Rust progress commands call the authenticated sidecar and never execute
  progress SQL. Successful PKL writes use the existing best-effort mirror;
  mirror failure marks SQLite dirty without losing the user mutation, and the
  existing desktop read repository falls back to API while dirty.
- Notes remain SQLite-authoritative and are not touched by add/delete progress.
  Mindmap, document, folder, and sync metadata are not sent as whole-project
  replacement payloads.
