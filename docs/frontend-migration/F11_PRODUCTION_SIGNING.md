## Current Distribution Trust Policy

The current project-owner policy accepts unsigned, ad-hoc, or self-signed
distribution artifacts. Official Apple Developer ID, notarization, and
Windows Authenticode are recommended future hardening, but their absence is a
known release limitation (`P1`), not a current `P0` by itself.

Users may see Gatekeeper's unidentified-developer/open warning on macOS and
Microsoft Defender SmartScreen's unrecognized-app warning on Windows. These
warnings must be described in release notes and support instructions; they
must not be bypassed by weakening application security checks.

OS trust is separate from artifact integrity. Every artifact still requires
commit provenance, architecture/package inspection, SHA-256 recording, and
the updater protocol's own cryptographic verification where that protocol is
used. Missing OS certificates must never be used as a reason to disable Tauri
updater signature verification.

## Optional future production-hardening path

The existing `scripts/sign-notarize-macos.sh` and
`scripts/sign-windows-artifacts.ps1` remain fail-closed optional paths. When
enabled, they must fail if credentials are absent, sign with a secure
timestamp, and verify the result. The macOS script now places the separately
signed migration helper inside the notarized DMG so that the notarization
ticket covers the helper container as well.

Required future evidence is:

```text
macOS: Developer ID → hardened runtime → notarize → staple → codesign/spctl
Windows: sign app/helper/installer → signtool/Get-AuthenticodeSignature
```

This is not a current release gate under the accepted distribution policy.
The Tauri updater key remains a separate security gate: its public key must be
embedded in the release overlay, its `.sig` must be generated by the matching
private key, and invalid signatures must be rejected.
