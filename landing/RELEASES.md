# Обновление загрузок WORTA Desktop

`releases.json` — статический список загрузок, который читает `script.js`. Он содержит отдельную запись для Windows x64, macOS Apple Silicon и macOS Intel. HTML менять при выпуске не нужно.

## Текущий статус

Кнопки загрузки сейчас выключены. Найденные установщики относятся к `nfprogress`: `frontend/src-tauri/tauri.conf.json` задаёт `productName: nfprogress`, а GitHub-релиз v5.3.9 назван `Release nfprogress 5.3.9`. Старый WordPress-механизм использует `/app/update_manifest.json`; опубликованный манифест сообщает Windows 5.3.9 и macOS 5.3.10. HEAD-запросы к этим файлам возвращают 200, но доступность файла не подтверждает, что он собран и квалифицирован как WORTA. Поэтому эти URL не включены в `releases.json`.

## Проверенная публикация

После того как настольная сборка WORTA прошла проверки и установщики опубликованы по постоянным HTTPS-ссылкам, подготовьте кандидатный JSON с тем же форматом и всеми тремя платформами. Для каждой платформы используйте один из статусов:

- `available`: версия и ссылка на опубликованный файл;
- `preparing`: версия собирается или проходит проверку, ссылки нет;
- `unavailable`: сборка не поддерживается или временно не доступна, ссылки нет.

Пример записи:

```json
{
  "platform": "macos-arm",
  "status": "available",
  "version": "6.1.0",
  "url": "https://github.com/nevskyforever/nfprogress/releases/download/v6.1.0/worta-macos-arm-6.1.0.dmg",
  "message": "Для Apple Silicon"
}
```

Скрипт принимает путь к полному кандидатному файлу и заменяет `releases.json` только после проверок:

```sh
python3 landing/update_releases.py /path/to/release-candidate.json
```

Он требует ровно одну запись для каждой платформы; проверяет статус, формат версии, соответствие версии, архитектуры и расширения имени файла, HTTPS и разрешённые домены; отправляет HEAD-запрос через системный `curl` (с обычной проверкой TLS); проверяет статус ответа, конечный домен после перенаправления и непустой размер, если сервер его сообщает. Он не скачивает установщики. Не позволяет удалить уже доступную платформу или понизить её версию. Запись выполняется временным файлом и атомарной заменой, поэтому ошибка проверки оставляет прежний `releases.json` без изменений.

После успешной команды проверьте diff и страницу, затем закоммитьте/отправьте `landing/releases.json` и опубликуйте этот файл на SpaceWeb. Скрипт не создаёт Git-коммит, не выполняет push и не загружает файл на сервер.

## Автоматизация релизного процесса

Пока `update_releases.py` — подготовленный ручной шаг, его запуск не подключён к сборке или GitHub Actions. Для полного автоматического обновления workflow должен вызвать его только после успешной квалификации и публикации установщиков, с кандидатным JSON, сформированным из фактических release assets. Затем workflow должен опубликовать новый `releases.json` на SpaceWeb. Такое изменение `.github/workflows/build.yml` и выдачу workflow SSH-доступа следует отдельно согласовать; на этом этапе инфраструктура не менялась.
