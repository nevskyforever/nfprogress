# C11 — Client Crypto Module

## Scope and dependency

C11 provides an isolated, byte-oriented TypeScript module at `frontend/src/crypto/`.
It is not cloud sync, storage, a key vault, or an unlock UI. The sole production
dependency is `libsodium-wrappers-sumo` **0.8.4** (and its transitive
`libsodium-sumo` 0.8.4), locally bundled by Vite. The sumo distribution is used
because it exports `crypto_pwhash` with Argon2id.

`getSodium()` awaits the one shared `sodium.ready` promise, so concurrent callers
cannot race library initialization. Sodium supplies CSPRNG, Argon2id, XChaCha20-
Poly1305-IETF, and best-effort `memzero`; Web Crypto supplies HKDF-SHA-256.

## Keys and KDF

AMK, KEK, derived Object Key, and Recovery Key are exactly 32 bytes (256 bits).
AMK and Recovery Key are independently generated by libsodium CSPRNG. AMK is not
derived from either account authentication password or any server credential.

The C11 password KDF record is an in-memory, storage-neutral structure:

```text
{ kdf_version: 1, algorithm: "argon2id13", salt: Uint8Array(16),
  opslimit: 2, memlimit: 67108864 }
```

It invokes `crypto_pwhash(..., crypto_pwhash_ALG_ARGON2ID13)` explicitly, with
the UTF-8 passphrase and the parameters in the record. It never uses
`ALG_DEFAULT` or silently retries at a weaker cost. The v1 baseline is libsodium
interactive (2 operations, 64 MiB); final Desktop/Android/Web calibration must
be confirmed before production E2EE activation. An OOM or unsupported runtime is
a typed failure, not permission to lower the KDF parameters.

## Canonical identities, HKDF, and AAD

All required identity fields are non-empty Unicode scalar-value strings, UTF-8
encoded, and bounded: user/project/entity IDs at 512 bytes and entity type at
128 bytes. Lone UTF-16 surrogates and oversize values reject. Fields are always
ordered `user_id`, `project_id`, `entity_id`, `entity_type`; every variable field
is a four-byte unsigned big-endian byte length followed by its UTF-8 bytes.

Object-key HKDF v1 is:

```text
IKM = AMK
hash = SHA-256
salt = UTF-8("worta/hkdf/object-key/salt/v1")
info = ASCII("worta/object-key/v1") || 0x01 || 0x01 || fields
output = 32 bytes
```

The two one-byte values in `info` are respectively context format version 1 and
crypto format version 1. Object AEAD AAD is independent:

```text
ASCII("worta/object-aad/v1") || 0x01 || 0x01 || fields
```

The first byte is AAD format version 1 and the second is crypto format version 1.
Revision and timestamps are intentionally absent. For compatibility testing, with
AMK = 32 bytes of `0x07` and the UTF-8 fields `user-α`, `project-β`, `entity-γ`,
`document`, context bytes are:

```text
776f7274612f6f626a6563742d6b65792f7631010100000007757365722dceb10000000a70726f6a6563742dceb200000009656e746974792dceb300000008646f63756d656e74
```

and the resulting HKDF Object Key is:

```text
6bc270db196c49959307057b293d028a41d1c1aeb2e78a1a8e6f2d79d7194147
```

## AEAD envelopes

All encryption uses libsodium combined-mode XChaCha20-Poly1305-IETF: a 32-byte
key, a fresh CSPRNG 24-byte nonce per encryption, and ciphertext including the
16-byte authentication tag.

Object envelope v1:

```text
{ crypto_version: 1, aad_version: 1, nonce: Uint8Array(24), ciphertext: Uint8Array }
```

Password AMK wrapper v1:

```text
{ wrapping_version: 1, crypto_version: 1, kdf: Argon2idKdfRecord,
  nonce: Uint8Array(24), ciphertext: Uint8Array }
```

Its AAD is `ASCII("worta/amk/password-wrap/v1") || 0x01`. Recovery AMK wrapper
v1 is `{ wrapping_version: 1, crypto_version: 1, nonce, ciphertext }`, uses no
KDF, and its separate AAD is `ASCII("worta/amk/recovery-wrap/v1") || 0x01`.
Records deliberately carry raw bytes only; C11 defines no C13 database schema or
JSON/network DTO.

## Failure and secret lifecycle

The public failure categories are `unsupported_version`, `invalid_format`,
`invalid_key_length`, `kdf_failed`, `decrypt_failed`, and `runtime_unavailable`.
Unknown versions, malformed fields/nonces, incorrect key length, damaged data,
incorrect AAD, or wrong passphrase/Recovery Key fail closed. Errors contain no
keys, passphrases, plaintext, or ciphertext.

Temporary KEKs and Object Keys are erased with `sodium.memzero()` after use; the
temporary AMK copy made for Web Crypto HKDF is overwritten. Returned keys and
caller-owned AMKs are never unexpectedly cleared. JavaScript/WebAssembly garbage
collection cannot guarantee complete memory zeroization.

## Deliberately deferred

C11 does not persist or transmit any AMK/KEK/Object Key/Recovery Key/passphrase;
does not use localStorage, sessionStorage, IndexedDB, cookies, Keychain, DPAPI,
or mobile keystores; and does not add server schema, blobs, ciphertext uploads,
initial upload, Sync Engine, or an unlock/recovery UI. C8 remains gated with
`encryptedInitialUpload = false`; C9 remains metadata-only.

C12 still needs the dedicated security/regression stage. C13 must define encrypted
server records and DTO encoding, C16/C20 native secure storage and sync lifecycle,
and C21 trusted-Web storage/CSP/authentication boundaries. Attachment chunking and
final KDF platform calibration remain open.
